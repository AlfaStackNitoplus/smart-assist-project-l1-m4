Tips to complete L1M4, written as a quick reference for implementation and review.

1) Mock Data

  • Maintain mock/test data in one place: src/app/assets/mock-data.ts.
  • When you add a new menu item, update both menus and roleMenuMapping so it appears for the correct roles.
  • Keep mock data consistent with the interfaces in src/app/core/models/.

2) Login & Navigation Flow

  • Login screen: src/app/features/auth/login/.
  • Validate inputs, handle invalid login with a clear message, and keep navigation role-based using UserRole.
  • Store the logged-in user in shared state so other screens can react (service + Observable pattern).

3) Role-Based Menu Rendering

  • Generate the side menu from role↔menu mapping (don’t duplicate role checks in multiple templates).
  • Prefer consuming menus as an Observable and rendering with AsyncPipe in layouts.
  • Use structural directives (@for/*ngFor, @if/*ngIf) for role-specific blocks.

4) Tickets: Filtering + MatTable

  • Keep role-based visibility + status filtering in services (components should not contain filtering logic).
  • Expose tickets as Observable<Ticket[]> and render via AsyncPipe.
  • Keep MatTable columns consistent across roles and include a clear No data state.

5) UI Highlighting & Reusable Directive

  • Use [ngClass]/[ngStyle] for highlighting rules (status/priority) in a declarative way.
  • Apply the reusable hover/row interaction directive: src/app/shared/directive/interactive-row.ts (appInteractiveRow).

6) Pipes

  • Use built-in pipes where possible and the custom status formatting pipe (ticketStatus) for readable labels.
  • Use the json pipe only for debugging (Test Data tab), not for final UI.

7) Quick Checks Before Final Submission

  • Lifecycle: load data only in ngOnInit, UI refs in ngAfterViewInit, cleanup in ngOnDestroy.
  • No nested subscriptions; prefer RxJS operators (map, filter, switchMap) and AsyncPipe.
  • Verify role-based menus and ticket visibility work correctly for each role.

Project Folder Structure – L1M4

The application follows a feature-based and scalable folder structure, separating core components, layouts, and feature modules. 

src/
 └── app/
     ├── core/
     │   ├── components/
     │   │   ├── header/
     │   │   └── footer/
     │   ├── services/
     │   │   ├── ticket.service.ts/
     │   │   └── user.service.ts/
     │   └── models/
     │
     ├── features/
     │   ├── auth/
     │   │   └── login/
     │   ├── support-engineer/
     │   ├── supervisor/
     │   ├── user/
     │   └── user-manual/
     │
     ├── layouts/
     │   ├── auth-layout/
     │   └── main-layout/
     │
     ├── app.routes.ts
     ├── app.ts
     └── app.config.ts
  • Core: Shared components like Header & Footer, and shared services.
  • Features: Modules such as Auth, Support Engineer, Supervisor, User, User Manual.
  • Layouts: Separate layouts for authentication and main app.
  • Routing: Centralized route configuration in app.routes.ts.
